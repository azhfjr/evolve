# Task/project deletion and audit follow-up

18 October 2026. This continues the owner's request to audit functions, flows and design across Evolve, correct disproportionate popup containers, and add deletion of projects and tasks. The approved popup revision is already in production at `evolve-rensist.vercel.app` from source `c3f8bb0611cd52842214794be5458fa74586ba30` (deployment `dpl_EJ73rCkSnVux8fnaMxSyjXsj3Eyy`). The deletion functionality described here is a separate change awaiting review and production approval.

## Behavior and data ownership

Only the configured sole administrator can delete tasks or projects. Normal members retain the existing shared-task editing permissions; deletion does not expand them. A signed-in actor, active membership/valid configured admin, same-origin mutation, strict payload, current version and request identity are checked on the server. A stale version fails before changes are committed. Retrying the same request returns its saved outcome; a deleted task/project cannot reappear through replay of its earlier create/import receipt.

- **Task:** Delete task is available from list/board action menus, Archive action menus and the existing-task editor. Confirmation names the task and explains the permanent removal of its comments, checklist and attachments. Activity entries remain with their task link cleared. Incoming legacy dependencies and parent/recurrence links are cleared without deleting other tasks. Later recurring tasks remain. Unsaved task/comment content must be saved or discarded before opening deletion from the editor. Archive remains the reversible alternative.
- **Project:** Delete project is available on the project page. Confirmation requires typing `DELETE` and states that project Cost items, Expense history and project attachments are permanently removed. Every active and archived task is preserved in No project, with comments and task attachments. Activity history remains with its project link cleared. Work is detached in the database, including tasks beyond the current loaded page. This is the conservative default presented to the owner; no assumption authorizes deletion of their live records.
- **Files:** The transaction marks ready and pending entity attachments as deleting, immediately preventing new authorized reads, upload tokens and finalization. Physical removal runs after the response; the existing tombstone hold/retry and maintenance sweep remain. An attachment reservation now checks entity existence under the same workspace lock as deletion, preventing a concurrent reservation from becoming a live orphan. Draft, avatar and unrelated project/task files retain their existing privacy and state.
- **Google Calendar:** Removal is a durable queued operation, not a synchronous promise that Google is immediately updated. Deletion increments the queued job generation before removing the task. The worker deletes its deterministic remote event even after the task is gone; existing leases prevent a stale in-flight write from erasing the newer cleanup job. Provider failures remain retryable. Existing job owners remain eligible for a generation bump after reassignment or Calendar scope/settings changes, including when deletion follows the first worker’s completion. Disconnecting or revoking access retains pending write identities and leases with a new generation, while erasing tokens and preventing provider requests until the owner reconnects. Reconnecting the same calendar queues retained events whose tasks were deleted while disconnected; an OAuth callback rechecks its return task under the workspace lock and falls back to Calendar settings if that task disappeared. Task preferences are removed and OAuth return links are cleared. Preserved tasks whose versions change are queued for synchronization too.
- **Navigation:** Successful task deletion closes its editor and removes the task URL; project deletion returns to Projects and focuses the heading. Missing/deleted project routes show a clear recovery state and cannot create tasks or open a create-project form. Lists invalidate their server query. An open task retains its identity when a refresh no longer includes it, rather than becoming a create-task form. Saved views referencing a missing project fall back to All tasks with an explanation; templates referencing it apply to No project.

## Design audit

The existing shared popup layout remains the base: 480 px standard width, bounded viewport height, outside gutters, 20 px desktop/16 px mobile padding. Deletion content scrolls independently while Cancel/Delete remain visible. Long item names wrap; the project confirmation input respects the mobile input scale. Destructive actions use the existing red treatment with readable dark-mode text. Cancellation restores the originating control when it still exists; completed removal focuses the workspace heading. Network errors remain inside the confirmation and retain the request identity for retry.

## Verification

Acceptance tests are in `tests/database.integration.test.ts` and `e2e/entity-deletion.spec.ts`. They use explicitly disposable local PostgreSQL databases and isolated browser demo data. The database tests include preservation of 501 project tasks across active/archive states and a file reservation racing deletion. Browser tests exercise actual authenticated UI → API → persistence → reload, cancellation, denied permissions, stale versions, response loss/retry and responsive confirmations. The initial validation passed 87 unit/PostgreSQL tests and nine deletion browser scenarios. Independent review then identified Calendar reassignment, reconnect, callback and first-write disconnect/revocation races; each was reproduced by a failing PostgreSQL regression before the repair. The complete workspace regression result and exact source SHA are recorded in the associated pull request after the final checks finish.

## Migration, rollout and recovery

`0011_calendar_task_deletion.sql` removes only the task foreign keys on `calendar_job` and `calendar_event`; these rows must survive the task long enough to remove its remote event. Member foreign keys and composite primary keys remain. No stored task, project, event or financial row is deleted by applying the migration. The health route requires both the existing private-draft migration and migration 0011. Review/apply it before enabling this version in production. Do not edit earlier applied migrations.

The current popup production approval does not authorize deployment of this deletion release. A demo-only preview can be built without migrating any shared production database; its UI preview is not proof of backend migration readiness. Production must retain private drafts/tombstones, per-currency amounts and the new Calendar cleanup worker.

Application rollback cannot restore a record the administrator explicitly deletes. If rolling UI back, retain the new cleanup worker/schema or first drain and verify all deletion jobs/events with this worker; an older worker would discard jobs for missing tasks without removing remote events. Do not re-add the removed foreign keys while cleanup rows reference deleted tasks, do not automatically reset/restore the database, and do not use live organization data as test fixtures. Provider snapshot recovery, if needed, is a separate owner decision.
